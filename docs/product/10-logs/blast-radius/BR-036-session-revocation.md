## 3. The graph cannot see this sub-step's most important edge

The session is issued in TypeScript (`apps/web/src/auth/guest.ts`) and stored and
validated in Python (`services/identity/src/sessions.py`). **They agree only if
both produce byte-identical token hashes**, and no edge in the graph connects them
— `BR-025` recorded that the graph does not traverse the TS/Python boundary.

So the coupling is held by a test rather than by analysis, and the test is written
to be honest about it: the vector in
`test_the_hash_format_matches_the_typescript_implementation` was generated by
**running the TypeScript implementation**, not the Python one. A vector produced by
the code under test proves only that the code agrees with itself.

A mismatch would surface as `unknown_token` — indistinguishable from a forged
token — so the symptom would not have pointed at the cause.

## 7. Mandatory data-flow inspection

**Flow:** token minted (TS) → hashed → stored (Python) → presented → validated →
revoked → refused.

| Hazard | Control | Evidence |
| --- | --- | --- |
| A revoked session running to its natural expiry | Revocation checked **at validation**, before expiry | Seeded and killed |
| Revocation losing the evidence it happened | Stamps `revoked_at`; **the app role has no DELETE privilege** on either table | Seeded; R7 asserts `permission denied` |
| A revocation nobody can attribute | `revoked_reason` from a closed vocabulary; a CHECK constraint makes reason and timestamp inseparable | Two tests, one at the DB level |
| Sign-out on one device ending all of them | `revoke_session` targets one row | Tested |
| Revoke-all reaching another user | Scoped by `(organization_id, user_id)` | Seeded with an over-broad predicate and killed |
| Revoking a role leaving a live token | `revoke_membership` cascades **in the same transaction** | Seeded and killed |
| A raw token in the database | Only the hash is inserted | Seeded and killed |
| A raw token in the audit trail | The guest audit subject is a constant | Structural |
| Cross-tenant read or revoke | RLS + `FORCE`; R7 asserts both directions | R7 18/18 |
| A guest session leaking across guests | No tenant column exists to get wrong; isolation is the unguessable 256-bit token, stated in the policy comment | Schema-asserted |

## 8. Two findings about the tests, not the code

**My first mutation test of the FORCE-RLS check was invalid.** I dropped `FORCE`
on `sessions` in the live database and the suite still passed — because the suite
**re-applies the migration before asserting**, repairing the drift it then checks.
A valid seed had to go in the migration file. Worth stating plainly: *a suite that
heals the condition it tests cannot fail on it*, and that was not visible until
someone tried.

**The FORCE-RLS assertion listed three tables by name.** Adding a fourth
tenant-scoped table would have left it unchecked while the assertion still passed
— the same "asserting the current extent of something designed to extend" pattern
as `BUG-021` and the stale assertions in STEP-004 `.02`/`.03`. It is now derived
from the schema: *every table with an `organization_id` must force RLS*. The next
tenant table is covered by whoever creates it, without them knowing this file
exists.
